# Reusable prompt: hand off a hardware project to another session

For a physical build whose history lives in a chat rather than a repo.
Paste into the session where the project was actually built, then give the
resulting markdown file to whoever is writing it up.

Companion to `project-rundown-prompt.md`, which covers software projects
that have a repository to verify against.

---

I need a complete written handoff for this project so someone who was never
part of this conversation can write it up accurately for my portfolio and
resume. Go back through our **entire** conversation, including the earliest
messages, and don't summarise the specifics away — the details are the point.

Write it as a single markdown file. Structure:

1. **What it is** — one paragraph, plus one sentence I could say out loud to
   someone who has never seen one.

2. **What it's made of** — the actual parts with real specifications: motor
   type and origin, voltage and current, controller or driver board, power
   supply, bearings, fasteners, frame material and dimensions. Part numbers
   where we used them. If a number was never measured or confirmed, say so
   rather than estimating.

3. **How it works** — two chains, described separately: the mechanical path
   (what drives what, through what) and the control path (what tells the
   motor what to do, and how it knows). Plain language, no jargon without a
   one-line definition.

4. **How it was built** — the actual sequence. What was designed in CAD, what
   was 3D printed, machined, welded or bought. Where tolerances or fit
   mattered and how they were achieved.

5. **Design decisions worth being asked about** — every point where a
   different choice was available. State what was chosen, what was rejected,
   and the reason. Include anything we decided *not* to build and why, and
   anything we changed our minds about after testing.

6. **What went wrong** — the most important section. For each problem:
   the symptom, what we thought it was at first, **how it was actually
   diagnosed**, the fix, and whether the fix addressed the root cause or the
   instance. Include failures that were only visible under load or over time,
   not just the ones that stopped it working outright.

7. **Safety** — anything about torque limits, current limits, how power gets
   cut in a hurry, and whether the build was deliberately sized to stay below
   a threshold. If safety was not designed for, say that plainly.

8. **Current state** — is it finished, does it work, is it used regularly,
   and what is still unbuilt, untested or known-broken.

9. **Who did what** — how much of the design was mine versus copied from an
   existing build, a kit, or generated by AI. Be specific and unflattering
   where that's accurate; I would rather claim less and defend it.

10. **Photographs worth taking** — for each major point above, say which photo
    would show it best, so I know what to shoot.

11. **Unverified** — everything in this document that is assumption, memory,
    or a number nobody measured. I need this list so none of it reaches a
    resume as fact.

**Rules:** real numbers over adjectives. Never invent a specification to fill
a gap — write "not measured" instead. Write for someone who is not an
engineer but is not stupid. Don't inflate: no "production", "advanced" or
"professional-grade" on a one-off build in a bedroom.
